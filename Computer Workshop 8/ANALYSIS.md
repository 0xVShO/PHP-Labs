# Перевірка безпеки застосунку

## 1. Захист від SQL-ін'єкцій
* Вразливість: Можливість маніпуляції SQL-запитом через параметр фільтра за статусом
* Payload для перевірки: `api.php?resource=tickets&status=open' OR '1'='1`
* Виправлення: В архітектурі всього застосунку та у файлі `api.php` **відсутня** пряма конкатенація рядків із `$_GET`/`$_POST`. Для всіх звернень до БД застосовуються підготовлені запити PDO:

```php
// Код із api.php:
$sql .= " WHERE t.status = :status";
$params[':status'] = $statusFilter;
$stmt = executeQuery($pdo, $sql, $params);
```
## 2. Захист від XSS-атаки
* Вразливість: Можливість інтегрування стронього Java Script коду через поля без екранування
* Payload для перевірки: `<script>alert("Hello XSS")</script>`
* Виправлення: В початковому коді, на стороні фронтенду вразливості XSS-атаки не було, так як у минулих лабораторних роботах, після введення правок, проблема була усунута. Однак, на северній стороні застосунку, проблема зберігання шкідливого XSS-коду залишалась. Хоч для БД це не містить ніякої небезпеки, проте при маштабуванні проєкту, якщо на якійсь сторінці текст буде виводитись як є, то фактично цей шкідливой код спрацює. Через це, в `api.php` було додано спеціальний метод `htmlspecialchars()`:

```php
// Код із api.php:
$subject = htmlspecialchars(trim($subjectRaw), ENT_QUOTES, 'UTF-8');
$description = htmlspecialchars(trim($descriptionRaw), ENT_QUOTES, 'UTF-8');
```

# 3. Захист від CSRF
* Вразливість: Можливість закрити або змінити статус тікета з іншого сайту через підроблений POST запит від іншого імені
* Payload для перевірки: Відправка POST запиту до `api.php?resource=tickets` із параметром `action=update_status` в обхід UI без дійсного токена
* Втправлення: Згенеровано `csrf_token` у сесії (в index.php), який передається в meta-тезі та перевіряється на сервері:

```php
// Код із api.php:
$submittedToken = $_POST['csrf_token'] ?? '';
if (empty($submittedToken) || !hash_equals($_SESSION['csrf_token'] ?? '', $submittedToken)) {
    http_response_code(403);
    echo json_encode(['success' => false, 'error' => 'Відмовлено в доступі: недійсний CSRF-токен.']);
    exit;
}
```

## 4. Захист небезпечних дій (Видалення)
Видалення тікета працює суворо через POST-запит з передачею CSRF-токена та запитує явне підтвердження користувача перед викликом через `confirm()` у JavaScript.

## 5. Обробка помилок
Усі звернення до API обгорнуті в глобальний блок `try...catch (Throwable $e)`. Деталі помилок (наприклад, PDOException) пишуться в системний лог через `error_log()`, а користувачеві повертається безпечне повідомлення `{"success": false, "error": "Внутрішня помилка сервера..."}` зі статусом 500.
